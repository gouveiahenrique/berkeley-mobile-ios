# API & Interface Standards

This repository is a mobile (iOS) application. There is no backend HTTP API implemented in this repository. This document covers how the application communicates with its backend (Firebase) and external services.

## Networking Layer

- The application uses Google Cloud Firestore as its data backend. Per `README.md:28`, "The application pulls data from Google Cloud Firestore," and the production API key/`GoogleService-Info.plist` are not included in the repository.
- The repository implements Firestore access in two patterns:
  1. **`DataSource` protocol conformers** (`berkeley-mobile/Data/DataSource.swift:11-16`): each conforming type implements a static `fetchItems(_:)` method using a completion-handler callback (`typealias completionHandler = (_ resources: [Any]) -> Void`, line 12) and exposes a static `fetchDispatch: DispatchGroup` to prevent duplicate concurrent fetches. Observed conformers: `MapDataSource` (`berkeley-mobile/Home/Map/MapDataSource/MapDataSource.swift:15`), `LibraryDataSource` (`berkeley-mobile/Home/Libraries/LibraryDataSource/LibraryDataSource.swift:14`), `GymDataSource` (`berkeley-mobile/Home/Fitness/GymDataSource/GymDataSource.swift:14`), `GymClassDataSource` (`berkeley-mobile/Home/Fitness/GymClassDataSource/GymClassDataSource.swift:14`). These are invoked through the central `DataManager.fetch(source:_:)` (`berkeley-mobile/Data/DataManager.swift:65-87`), which caches results per source and calls the completion handler on the main queue.
  2. **Direct Firestore access with Swift concurrency (`async`/`await`)** inside view models/services, without going through `DataManager`: `BMNetworkingManager` (`berkeley-mobile/Data/BMNetworkingManager.swift:12-38`, methods `fetchSafetyLogs()` and `fetchResourcesCategories()`), `EventsDataService` (`berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:35-74`, method `fetchEventsGroupedByDate()`), and `DiningHallsViewModel` (`berkeley-mobile/Home/Dining/DiningDataSource/DiningHallsViewModel.swift:17-104`, methods `fetchDiningHalls(withAdditionalData:)` and `fetchDiningHallsAdditionalData()`).
- The repository defines named Firestore collection endpoints as file-local constants, e.g. `kMapEndpoint = "Map Marker"` (`berkeley-mobile/Home/Map/MapDataSource/MapDataSource.swift:13`), `kLibrariesEndpoint = "Libraries"` (`berkeley-mobile/Home/Libraries/LibraryDataSource/LibraryDataSource.swift:12`), `kGymsEndpoint = "Gyms"` (`berkeley-mobile/Home/Fitness/GymDataSource/GymDataSource.swift:12`), `kGymClassesEndpoint = "Gym Classes"` (`berkeley-mobile/Home/Fitness/GymClassDataSource/GymClassDataSource.swift:12`), `kEventsDataServiceEndpoint = "Events"` (`berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:14`), `kDiningHallEndpoint = "Dining Halls V2"` and `kDiningHallAdditionalDataEndpoint = "Dining Halls"` (`berkeley-mobile/Home/Dining/DiningDataSource/DiningHallsViewModel.swift:14-15`), and collection names referenced via `BMConstants` in `BMNetworkingManager.swift:21,32` (`BMConstants.safetyLogsCollectionName`, `BMConstants.resourceCategoriesCollectionName`).
- Data decoding: some services parse raw `[String: Any]` dictionaries manually (e.g. `MapDataSource.parseMarker(_:)`, `berkeley-mobile/Home/Map/MapDataSource/MapDataSource.swift:38-64`; `LibraryDataSource.parseLibrary(_:docID:)`, `berkeley-mobile/Home/Libraries/LibraryDataSource/LibraryDataSource.swift:39-53`), while others decode directly into `Codable` structs via Firestore's `data(as:)` (e.g. `BMNetworkingManager.fetchSafetyLogs()` decodes into `BMSafetyLog: Codable`, `berkeley-mobile/Data/BMNetworkingManager.swift:24`; `EventsDataService` decodes into `BerkeleyEventsDaySnapshot: Codable`, `berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:16,48`).

## Authentication

- The repository imports `Firebase/Auth` and `GoogleSignIn` (`Podfile:13-14`). Specific authentication flow implementation using these was not found within the areas inspected in this analysis pass.

## Push Notifications / Messaging

- The repository implements Firebase Cloud Messaging integration: `AppDelegate` conforms to `MessagingDelegate` and `UNUserNotificationCenterDelegate` (`berkeley-mobile/AppDelegate.swift:56,75`), requests notification authorization (line 31), registers for remote notifications (line 32), and on receiving an FCM token, posts an internal `Notification.Name("FCMToken")` and subscribes the device to the `"all"` topic (`berkeley-mobile/AppDelegate.swift:77-87`).
- On notification tap, `AppDelegate.userNotificationCenter(_:didReceive:)` (`berkeley-mobile/AppDelegate.swift:64-69`) navigates the user to tab index 2 (Safety) of `TabBarController`.

## Internal Contracts (Errors & Callbacks)

- The repository defines a typed error enum, `BMError` (`berkeley-mobile/Data/BMError.swift:11-16`), covering calendar-integration failure cases (`eventAlreadyAddedInCalendar`, `insufficientAccessToCalendar`, `mayExistedInCalendarAlready`, `unableToFindEventInCalendar`), conforming to `LocalizedError` with user-facing messages (lines 18-31).
- Completion-handler-based APIs (the `DataSource` protocol and `DataManager.fetch`) do not surface errors to the caller through the completion handler; errors from Firestore in these paths are handled by printing to the console (e.g. `print("[Error @ MapDataSource.fetchItems()]: \(err)")`, `berkeley-mobile/Home/Map/MapDataSource/MapDataSource.swift:25`) rather than propagating to the UI.
- Newer `async`/`await`-based services surface failures to the UI via `@Published`/`@Observable` `alert: BMAlert?` properties, e.g. `SafetyViewModel.listenForSafetyLogs()` catches errors and sets `self.alert = BMAlert(title: "Failed To Fetch Safety Logs", message: error.localizedDescription, type: .notice)` (`berkeley-mobile/Safety/SafetyViewModel.swift:95-98`), and `EventsViewModel.deleteEvent(for:)`/`addAcademicEventToCalendar(_:)` present `BMAlert`s on `BMError` cases (`berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:124-150`).

## External Service Integrations

- Firebase Analytics: the repository logs custom analytics events via `Analytics.logEvent(_:parameters:)`, e.g. `"opened_academic_calendar"` and `"opened_campus_wide_events"` (`berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:94-100`), `"opened_food_screen"` (`berkeley-mobile/Home/HomeViewModel.swift:63-65`), `"point_of_interest_clicked"` (`berkeley-mobile/Home/Map/MapViewController.swift:376`), and `"opened_food"` (`berkeley-mobile/Home/Dining/DiningDataSource/DiningHallsViewModel.swift:93-95`).
- MapKit/CoreLocation: the repository uses `MKMapView`, `CLLocationManager`, and related types for the Map tab and user-location features (`berkeley-mobile/Home/Map/MapViewController.swift`, `berkeley-mobile/Data/BMLocationManager.swift`).
- Calendar (`EventKit`, inferred from `BMEventManager` usage in `EventsViewModel`): the repository adds/deletes events to/from the user's device calendar (`EventsViewModel.addAcademicEventToCalendar(_:)`, `deleteEvent(for:)`, `berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:124-150`). The `BMEventManager` implementation itself was not inspected in this pass.

Not applicable for this repository type: REST/GraphQL route definitions, server-side request lifecycle, request authentication middleware — this repository does not implement a backend service.
