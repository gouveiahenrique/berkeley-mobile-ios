# Code Conventions

Evidence for this document was gathered by inspecting representative files across `berkeley-mobile/` via CodeGraph and direct file reads. Statements describe observed patterns in inspected files, not an exhaustive audit of all 176 Swift files.

## Naming Conventions

- **`BM` prefix for shared/global types:** Many cross-feature model, manager, and utility types are prefixed `BM` (Berkeley Mobile), e.g. `BMColor`, `BMConstants`, `BMError`, `BMAlert`, `BMNetworkingManager`, `BMLocationManager`, `BMEventManager`, `BMEventCalendarEntry`, `BMGym`, `BMSafetyLog`, `BMResourceCategory`, `BMDiningHall`, `BMCachedAsyncImageView`, `BMActionButton`, `BMDrawerView`, `BMFilterButton`, `BMSegmentedControlView`, `BMTopBlobView`, `BMContentUnavailableView`, `BMAddedCalendarStatusOverlayView`. 28 top-level declarations with this prefix were found via `grep` in `berkeley-mobile/`. Feature-local types without cross-feature reuse (e.g. `DiningHallsViewModel`, `GuidesViewModel`, `TagView`) do not consistently use the prefix.
- **`ViewModel` suffix:** Types backing SwiftUI/UIKit screens are named `<Feature>ViewModel`, e.g. `SafetyViewModel`, `ResourcesViewModel`, `DebugViewModel`, `FeedbackFormViewModel`, `HomeViewModel`, `EventsViewModel`, `SearchViewModel`, `WeatherDataViewModel`, `NewsDataViewModel`, `HomeDrawerPinViewModel`, `GuidesViewModel`, `DiningHallsViewModel`, `GymOccupancyViewModel` (13 files match `*ViewModel.swift` under `berkeley-mobile/`).
- **`fileprivate`/private endpoint constants:** Firestore collection names are declared as `fileprivate let k<Name>Endpoint = "..."` at file scope immediately below the imports, e.g. `kGymsEndpoint` (`GymDataSource.swift`), `kDiningHallEndpoint`/`kDiningHallAdditionalDataEndpoint` (`DiningHallsViewModel.swift`), `kGuidesEndpoint` (`GuidesViewModel.swift`), `kFeedbackFormConfigEndpoint`/`kFeedbackResponsesCollection` (`FeedbackFormViewModel.swift`). Some (e.g. `NewsDataViewModel`) instead declare the endpoint name as a `private let` instance property.
- **Extension-per-concern for colors:** `BMColor` is extended in separate files named `Colors+<Concern>.swift` (e.g. `Colors+ActionButton.swift`, `Colors+Calendar.swift`, `Colors+Event.swift`, `Colors+GymClass.swift`, `Colors+MapMarker.swift`, `Colors+Resource.swift`, `Colors+StudyPact.swift`, `Colors+TagView.swift`, `Colors+Text.swift`, `Colors+AlertView.swift`) under `berkeley-mobile/Assets/Colors/`, each defining a nested `struct` (e.g. `struct ActionButton`) with `static var`/`static func` color accessors.

## File Organization

- Each feature has its own top-level folder under `berkeley-mobile/` (e.g. `Events/`, `Safety/`, `FeedbackForm/`, `Resources/`, `Today/`), and larger features further nest a `*DataSource/` subfolder for their models/view models (e.g. `Home/Dining/DiningDataSource/`, `Home/Fitness/GymDataSource/`, `Home/Fitness/GymClassDataSource/`, `Home/Map/MapDataSource/`, `Home/Libraries/LibraryDataSource/`, `Events/EventDataSource/`). See `docs/structure.md` for the full breakdown.
- Cross-feature protocols live under `berkeley-mobile/Data/ItemProtocols/`, one protocol per file (e.g. `HasImage.swift`, `HasLocation.swift`, `HasOpenTimes.swift`, `CanFavorite.swift`, `SearchItem.swift`).
- Extension files follow a `<Type>+<Concern>.swift` naming pattern under `berkeley-mobile/Utils/` (e.g. `Date+Extension.swift`, `UIView+Extensions.swift`, `String+Extension.swift`, `UserDefaults+Extension.swift`, `NSCoding+Extension.swift`).

## Recurring Implementation Patterns

- **`// MARK: -` section comments:** Used throughout to delimit logical sections within a file (44 files contain `// MARK: -` per repository search), e.g. `// MARK: - Safety`, `// MARK: - Resources` in `BMNetworkingManager.swift`; `// MARK: CalendarEvent Fields`, `// MARK: CanFavorite` in `BMEventCalendarEntry.swift`.
- **Singleton pattern via `static let shared`:** Used for cross-cutting managers, e.g. `DataManager.shared` (`DataManager.swift`), `BMNetworkingManager.shared` (`BMNetworkingManager.swift`), `BMLocationManager.shared` (`BMLocationManager.swift`).
- **Dependency injection via Factory (`FactoryKit`):** View models are registered as `Factory<T>` computed properties on `Container` in `berkeley-mobile/BerkeleyMobile+Injection.swift`, each with an explicit scope (`.shared`, `.singleton`, or the default/unscoped), and consumed in SwiftUI views via `@InjectedObservable(\.<name>)`. Some registrations are `@MainActor`-isolated closures (e.g. `homeViewModel`, `eventsViewModel`, `gymOccupancyViewModel`).
- **Two coexisting observable-state styles:** Newer view models use the `@Observable` macro (`Observation` framework) with `@ObservationIgnored` for non-observed stored properties (e.g. `DiningHallsViewModel`, `FeedbackFormViewModel`, `WeatherDataViewModel`, `NewsDataViewModel`). Older view models use `ObservableObject` with `@Published` properties (e.g. `SafetyViewModel`, `ResourcesViewModel`). Both styles are present in the current codebase; there is no indication one has fully replaced the other.
- **`async`/`await` for Firestore fetches, wrapped in `Task { }` from `init()`:** View models that own their data-fetch (as opposed to going through `DataManager`) typically kick off loading in `init()` via `Task { ... }` or `Task { @MainActor in ... }`, setting an `isFetching`/`isLoading` flag before and after, e.g. `DiningHallsViewModel.init()`, `SafetyViewModel.init()`, `ResourcesViewModel.init()`, `NewsDataViewModel.init()`.
- **`do`/`catch` with `os.Logger` categories:** Firestore/network failures are logged through per-type `Logger` instances centrally declared as static properties in `berkeley-mobile/Utils/Logger+Ext.swift` (e.g. `Logger.diningHallsViewModel`, `Logger.newsDataViewModel`, `Logger.feedbackFormConfig`), each constructed with `subsystem: Bundle.main.bundleIdentifier!` and `category: String(describing: <Type>.self)`.
- **User-facing error surfacing via `BMAlert`:** Some (not all — see `docs/api-standards.md`) view models expose an `@Published var alert: BMAlert?` / `var alert: BMAlert?` populated on catch blocks, consumed by SwiftUI `.alert` modifiers per the `BMAlert` struct in `berkeley-mobile/Common/BMAlert.swift`.
- **Custom property wrappers for data sanitization:** `@Display` (`berkeley-mobile/Data/PropertyWrappers/Display.swift`) trims whitespace/invalid characters from `String`/`String?` fields, used on model properties like `BMEventCalendarEntry.name`/`descriptionText`/`location`.
- **`NSCoding` conformance for local persistence of calendar entries:** `BMEventCalendarEntry` implements `encode(with:)`/`init?(coder:)` using a private nested `ArgumentNames` struct of string keys, mirroring the pattern in `berkeley-mobile/Utils/NSCoding+Extension.swift`.
- **Typed `UserDefaults` keys:** All `UserDefaults` access goes through an `enum UserDefaultsKeys: String` and typed extension methods (`set(_:forKey:)`, `integer(forKey:)`, `data(forKey:)`, `increment(forKey:)`) defined in `berkeley-mobile/Utils/UserDefaults+Extension.swift`, rather than raw string keys at call sites.
- **`#if DEBUG` gating:** Debug-only functionality (the Debug tab view model) is registered conditionally in `berkeley-mobile/BerkeleyMobile+Injection.swift` using `#if DEBUG ... #endif`.

## Architectural Patterns

- **MVVM-oriented separation:** Views (SwiftUI `View` structs or UIKit `UIViewController`/`UIView` subclasses) are paired with a `ViewModel` type that owns state and data-fetching; views read/observe the view model rather than performing fetches themselves (e.g. `DiningHallsView` reads `viewModel.diningHalls`/`viewModel.isFetching` from an injected `DiningHallsViewModel`).
- **Delegate-protocol composition for shared UIKit behavior:** Complex interactive behavior (drawer dragging/stacking) is implemented as protocol extensions with default implementations rather than base classes, e.g. `DrawerViewDelegate` (`berkeley-mobile/Drawer/DrawerViewDelegate.swift`) and `MainDrawerViewDelegate` (`berkeley-mobile/Drawer/MainDrawerViewDelegate.swift`), both constrained to `Self: UIViewController`.
- **Capability protocols for model composition:** Domain models adopt small, single-purpose protocols to opt into shared behavior/UI (e.g. `HasImage`, `HasLocation`, `CanFavorite`, `SearchItem`, `HasOpenTimes`) instead of a single large base class, as seen on `BMEventCalendarEntry: NSObject, NSCoding, Identifiable, BMCalendarEvent, HasImage, CanFavorite`.
