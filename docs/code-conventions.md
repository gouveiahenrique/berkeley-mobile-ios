# Code Conventions

## Naming Conventions

- **App-specific type prefix `BM`:** Many types that are not tied to a single feature screen use a `BM` prefix, e.g. `BMColor` (`berkeley-mobile/Assets/Colors/Colors.swift:13`), `BMNetworkingManager` (`berkeley-mobile/Data/BMNetworkingManager.swift:12`), `BMLocationManager` (`berkeley-mobile/Data/BMLocationManager.swift:26`), `BMError` (`berkeley-mobile/Data/BMError.swift:11`), `BMAlert` (`berkeley-mobile/Common/BMAlert.swift:12`), `BMEventCalendarEntry` (`berkeley-mobile/Events/EventDataSource/BMEventCalendarEntry.swift:11`), `BMSafetyLog` (`berkeley-mobile/Safety/SafetyViewModel.swift:12`).
- **`*ViewModel` suffix for observable state holders:** e.g. `SafetyViewModel`, `EventsViewModel`, `HomeViewModel`, `SearchViewModel`, `GuidesViewModel`, `GymOccupancyViewModel`, `DebugViewModel`, `FeedbackFormViewModel`, registered in `berkeley-mobile/BerkeleyMobile+Injection.swift`.
- **`*View` suffix for SwiftUI views** (e.g. `SafetyView`, `ResourcesView`, `TodayView`, `GuideDetailView`) vs. **`*ViewController` suffix for UIKit view controllers** (e.g. `MapViewController`, `DrawerViewController`, `GymDetailViewController`, `LibraryDetailViewController`) — the two suffixes are used consistently to distinguish the two UI frameworks in the same codebase.
- **`*DataSource` suffix for per-feature data-fetching types** conforming to the `DataSource` protocol (`berkeley-mobile/Data/DataSource.swift`), e.g. `MapDataSource`, `LibraryDataSource`, `GymDataSource`, `GymClassDataSource` (paths under `berkeley-mobile/Home/*/**DataSource/`).
- **`Has*` / `Can*` protocol naming for shared model capabilities:** `HasImage`, `HasLocation`, `HasName`, `HasOpenClosedStatus`, `HasOpenTimes`, `HasPhoneNumber`, `HasWebsite`, `CanFavorite` (all under `berkeley-mobile/Data/ItemProtocols/`).
- **`k`-prefixed file-private constants:** e.g. `kDataSources` (`berkeley-mobile/Data/DataManager.swift:12`), `kEventsDataServiceEndpoint` (`berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:14`), `kAnnotationIdentifier`/`kViewMargin` inside a nested `Constants` struct (`berkeley-mobile/Home/Map/MapViewController.swift:38-43`).
- **`// MARK: -` section comments** are used pervasively to delineate logical sections within a file (protocol conformance extensions, grouped functionality), e.g. `berkeley-mobile/AppDelegate.swift:37,54,74`, `berkeley-mobile/Data/BMNetworkingManager.swift:18,29`.

## File Organization

- One primary type per file, with the file name matching the primary type name (e.g. `BMLocationManager.swift` defines `BMLocationManager`, `DrawerViewDelegate.swift` defines `DrawerViewDelegate`).
- Feature code is organized by feature folder under `berkeley-mobile/` (`Home/`, `Events/`, `Safety/`, `Today/`, `Resources/`, `FeedbackForm/`), each folder containing that feature's views, view models, and data-source types together (see `docs/structure.md`).
- Protocol conformances are frequently implemented in a separate `extension` block, often in the same file, marked with a `// MARK: - <ProtocolName>` comment — e.g. `AppDelegate: UNUserNotificationCenterDelegate` (`berkeley-mobile/AppDelegate.swift:56`) and `AppDelegate: MessagingDelegate` (`berkeley-mobile/AppDelegate.swift:75`) are both declared as separate extensions of `AppDelegate` within the same file.
- Type extensions on foundation/UIKit types live in `berkeley-mobile/Utils/` as `<Type>+Extension.swift` or `<Type>+Extensions.swift` files (e.g. `Date+Extension.swift`, `CLLocation+Extension.swift`, `UIViewController+Extensions.swift`).
- Per-feature color and font constants are centralized under `berkeley-mobile/Assets/Colors/` as `Colors+<Feature>.swift` extensions on `BMColor` (e.g. `Colors+Event.swift`, `Colors+GymClass.swift`, `Colors+MapMarker.swift`), separate from the base `Colors.swift`.

## Architectural / Implementation Patterns

- **Singletons for cross-cutting managers:** `DataManager.shared` (`berkeley-mobile/Data/DataManager.swift:21`), `BMNetworkingManager.shared` (`berkeley-mobile/Data/BMNetworkingManager.swift:13`), `BMLocationManager.shared` (`berkeley-mobile/Data/BMLocationManager.swift:28`), `ImageLoader.shared` (referenced in `berkeley-mobile/Data/ItemProtocols/HasImage.swift:25,34`) — all instantiated via a `private init()` or `static let shared` pattern.
- **Factory-based dependency injection for ViewModels:** `berkeley-mobile/BerkeleyMobile+Injection.swift` registers ViewModel construction closures on a `Container` extension (from the `FactoryKit` Swift package), using `.shared` or `.singleton` scope modifiers. Consumers resolve dependencies with `@Injected(\.<property>)` (e.g. `berkeley-mobile/TabBarController.swift:15`) or `Container.shared.<property>.resolve()` (e.g. `berkeley-mobile/Home/Map/MapViewController.swift:81`), rather than constructing ViewModels directly.
- **Protocol-oriented shared behavior via default extensions:** e.g. `MainDrawerViewDelegate` provides default implementations (`dismissTop`, `coverTop`, `hideTop`, `showTop`, `moveCurrentDrawer`, `showMainDrawer`, `computeDrawerPosition`) in a `where Self: UIViewController` extension (`berkeley-mobile/Drawer/MainDrawerViewDelegate.swift:22-106`), and `DrawerViewDelegate` similarly supplies default `moveDrawer`/`computePosition`/`handlePan` implementations (`berkeley-mobile/Drawer/DrawerViewDelegate.swift:36-129`).
- **`async`/`await` for newer Firestore-backed data fetches:** e.g. `BMNetworkingManager.fetchSafetyLogs()` and `fetchResourcesCategories()` (`berkeley-mobile/Data/BMNetworkingManager.swift:20,31`) and `EventsDataService.fetchEventsGroupedByDate()` (`berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:40`) are declared `async throws`/`async` and called from `Task { ... }` blocks in `@MainActor`-annotated ViewModels.
- **Completion-handler/`DispatchGroup`-based fetching for older data sources:** `DataManager.fetch(source:_:)` uses a `DispatchGroup` per `DataSource` type plus a `completionHandler` closure (`berkeley-mobile/Data/DataManager.swift:65-87`) rather than `async`/`await`, indicating two coexisting concurrency styles in the data layer.
- **`@Observable` / `ObservableObject` for SwiftUI state:** newer ViewModels use the `Observation` framework's `@Observable` macro (e.g. `SearchViewModel` in `berkeley-mobile/Home/Search/SearchViewModel.swift:43`, `EventsViewModel` in `berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:77`), while `SafetyViewModel` uses the older `ObservableObject`/`@Published` pattern (`berkeley-mobile/Safety/SafetyViewModel.swift:57,63-69`) — both patterns coexist in the repository.
- **Custom UI primitives instead of system components:** the drawer/bottom-sheet system (`berkeley-mobile/Drawer/`) is a hand-built `UIPanGestureRecognizer`-driven implementation rather than a system sheet API.

## Error Handling

- App-specific error cases are modeled as a `LocalizedError`-conforming enum, `BMError` (`berkeley-mobile/Data/BMError.swift:11-31`), with human-readable `errorDescription` strings per case.
- User-facing error/notice presentation is modeled through a single `BMAlert` struct (`berkeley-mobile/Common/BMAlert.swift:12-27`) with a `type: BMAlertType` (`.action` or `.notice`) and an optional `completion` closure, assigned to a `@Published var alert: BMAlert?` on ViewModels (e.g. `SafetyViewModel.alert`, `berkeley-mobile/Safety/SafetyViewModel.swift:68`; `EventsViewModel.alert`, `berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:81`).
- Firestore decode failures are handled with `try?`/`compactMap`, silently dropping documents that fail to decode (e.g. `berkeley-mobile/Data/BMNetworkingManager.swift:24,35`), rather than surfacing a per-document error.
