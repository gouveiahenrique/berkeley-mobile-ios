# Code Conventions

## Naming

- **`BM` prefix**: applied to cross-cutting/shared types, not universally — 20 of 174 Swift files under `berkeley-mobile/` have filenames starting with `BM` (e.g. `BMAlert.swift`, `BMColor` in `Colors.swift`, `BMConstants.swift`, `BMError.swift`, `BMEventManager.swift`, `BMEventCalendarEntry.swift`, `BMNetworkingManager.swift`, `BMLocationManager.swift`). Feature-local types commonly omit the prefix (e.g. `HomeView.swift`, `EventsViewModel.swift`, `GymDataSource.swift`, `SafetyViewModel.swift`). The prefix is not applied consistently across the codebase — do not assume every shared type carries it.
- **View model naming**: `<Feature>ViewModel` (e.g. `HomeViewModel`, `SafetyViewModel`, `EventsViewModel`, `ResourcesViewModel`, `GuidesViewModel`, `DiningHallsViewModel`, `FeedbackFormViewModel`, `DebugViewModel`, `GymOccupancyViewModel`, `HomeDrawerPinViewModel`, `MapMarkersDropdownViewModel`, `MapUserLocationButtonViewModel`, `NewsDataViewModel`, `WeatherDataViewModel`, `SearchViewModel`, `CalendarViewModel`) — registered in `berkeley-mobile/BerkeleyMobile+Injection.swift`.
- **Data source naming**: `<Domain>DataSource` conforming to the `DataSource` protocol (`MapDataSource`, `LibraryDataSource`, `GymDataSource`, `GymClassDataSource`), each paired with a `private static func parse<Domain>(_:)` parsing helper.
- **Firestore collection constants**: declared `fileprivate let k<Domain>Endpoint = "<Collection Name>"` at the top of each `*DataSource.swift` file (e.g. `kMapEndpoint`, `kLibrariesEndpoint`, `kGymsEndpoint`, `kGymClassesEndpoint`), rather than centralized — contrast with `BMNetworkingManager`, whose two collection names (`safetyLogsCollectionName`, `resourceCategoriesCollectionName`) are centralized as `static let` constants on `BMConstants` (`berkeley-mobile/Data/BMConstants.swift`).
- **`UserDefaults` keys**: centralized in a `UserDefaultsKeys: String` enum (`berkeley-mobile/Utils/UserDefaults+Extension.swift`), accessed through typed `UserDefaults` extension methods (`set(_:forKey: UserDefaultsKeys)`, `integer(forKey:)`, `data(forKey:)`, `increment(forKey:)`) rather than raw string keys at call sites.

## File Organization

- One primary type per file, file name matching the type name (e.g. `DataManager.swift` defines `class DataManager`).
- Related small extensions are grouped by suffix pattern, e.g. `Colors+ActionButton.swift`, `Colors+AlertView.swift`, `Colors+Calendar.swift` etc. under `berkeley-mobile/Assets/Colors/`, each extending the base `BMColor` struct (`Colors.swift`) for a specific feature area, rather than putting all color definitions in one file.
- Extension files for standard library / UIKit types use the `<Type>+Extension.swift` or `<Type>+Ext.swift` naming pattern under `berkeley-mobile/Utils/` (e.g. `Date+Extension.swift`, `CLLocation+Extension.swift`, `Collection+Extension.swift`, `String+Extension.swift`, `TimeInterval+Ext.swift`, `NSCoding+Extension.swift`, `Logger+Ext.swift`).
- Feature folders pair a data source subfolder with the feature's views/view models directly inside the parent feature folder (e.g. `Home/Fitness/GymDataSource/`, `Home/Fitness/GymClassDataSource/`, `Home/Fitness/GymOccupancy/` all sit under `Home/Fitness/` alongside `FitnessView.swift`/`GymDetailViewController.swift`).
- `// MARK: -` section comments are used pervasively to group code within a file (93 occurrences across `berkeley-mobile/`), commonly separating stored properties, lifecycle methods, and private helpers, and marking sample/preview data sections (e.g. `// MARK: - Sample Data` in `SafetyViewModel.swift`).

## Architectural Patterns

- **Singleton pattern**: used for app-wide managers accessed via `static let shared`: `DataManager.shared` (`berkeley-mobile/Data/DataManager.swift`), `BMLocationManager.shared` (`berkeley-mobile/Data/BMLocationManager.swift`), `BMNetworkingManager.shared` (`berkeley-mobile/Data/BMNetworkingManager.swift`).
- **Dependency injection via `FactoryKit`**: feature view models are not instantiated directly by their consuming views/controllers; they are registered as `Factory<T>` properties on `Container` in `berkeley-mobile/BerkeleyMobile+Injection.swift` with an explicit lifetime scope per registration — `.shared` (weakly-retained shared instance) for most view models, `.singleton` for a subset (`diningHallsViewModel`, `guidesViewModel`, `gymOccupancyViewModel`, `homeViewModel`), and no scope modifier (a fresh instance per resolution) for `feedbackFormPresenter`, `feedbackFormViewModel`, and `debugViewModel`.
- **`ObservableObject` vs. `@Observable`**: both patterns coexist — 6 files use `ObservableObject` (Combine-based, e.g. `HomeViewModel: ObservableObject` with `@Published` properties) and 10 files use the newer `@Observable` macro. The choice is not uniform across view models in the inspected files; do not assume one over the other for an untouched view model without checking it directly.
- **Protocol-oriented domain modeling**: domain model capabilities are expressed as small, composable protocols under `berkeley-mobile/Data/ItemProtocols/` (`HasImage`, `HasLocation`, `HasName`, `HasOpenClosedStatus`, `HasOpenTimes`, `HasPhoneNumber`, `HasWebsite`, `CanFavorite`, `SearchItem`, `BMCalendarEvent`), which domain types (e.g. `BMEventCalendarEntry: NSObject, NSCoding, Identifiable, BMCalendarEvent, HasImage, CanFavorite`) conform to selectively depending on which capabilities they need.
- **Property wrapper for input sanitization**: `@Display` (`berkeley-mobile/Data/PropertyWrappers/Display.swift`) is applied to `String`/`String?` model fields intended for UI display, trimming whitespace and stripping the `�` replacement character on every write to `wrappedValue`.
- **`#if DEBUG` conditional registration**: `debugViewModel` is registered in the DI container only under `#if DEBUG` (`berkeley-mobile/BerkeleyMobile+Injection.swift`), matching the `berkeley-mobile/Debug/` folder's `DebugView`/`DebugViewModel` being development-only tooling.

## Error Handling

- The repository defines a single custom error enum, `BMError: Error` (`berkeley-mobile/Data/BMError.swift`), covering calendar-integration failure cases, conforming to `LocalizedError` with user-facing `errorDescription` strings via `NSLocalizedString`.
- `async throws` functions (`BMNetworkingManager.fetchSafetyLogs()`, `fetchResourcesCategories()`, `BMEventManager.addEventToCalendar(calendarEvent:)`, `deleteEvent(_:)`, `saveEvent(_:)`) propagate errors to callers rather than swallowing them; `SafetyViewModel.listenForSafetyLogs()` is the observed pattern for catching and surfacing such errors to the UI, via `catch { self.alert = BMAlert(...) }`.
- By contrast, the closure-based `DataSource.fetchItems` implementations (`GymDataSource`, `LibraryDataSource`, `GymClassDataSource`) only `print()` the Firestore error and return without calling `completion`, rather than throwing or surfacing an error object — this is a different, older error-handling style coexisting with the newer `async throws` + `BMError` pattern. Do not assume all data-fetch paths report errors to the UI.

## Logging

- Structured logging via `os.Logger`, with one `Logger` instance defined per view model/service in a single centralized extension file, `berkeley-mobile/Utils/Logger+Ext.swift` (e.g. `Logger.diningHallsViewModel`, `Logger.eventsDataService`, `Logger.guidesViewModel`, `Logger.openClosedStatusManager`, `Logger.feedbackFormConfig`, `Logger.homeDrawerPinViewModel`, `Logger.newsDataViewModel`, `Logger.weatherDataViewModel`), each using `subsystem: Bundle.main.bundleIdentifier!` and `category: String(describing: <Type>.self)`. Older code (the `*DataSource.fetchItems` implementations noted above) instead uses bare `print(...)` for error logging — both styles are present in the repository.
