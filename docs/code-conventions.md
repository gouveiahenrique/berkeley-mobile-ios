# Code Conventions

## Naming Conventions

- **App-specific types are prefixed `BM`** (Berkeley Mobile), e.g. `BMLibrary`, `BMGym`, `BMDiningLocation`, `BMSafetyLog`, `BMError`, `BMConstants`, `BMNetworkingManager`, `BMLocationManager`, `BMEventManager`, `BMAlert`, `BMCachedAsyncImageView`, `BMDrawerView`. This prefix is used consistently across `berkeley-mobile/Data/`, feature model files, and shared `Common/` components.
- **View models are suffixed `ViewModel`** and generally live alongside or in a sibling folder to their corresponding view, e.g. `berkeley-mobile/Home/HomeViewModel.swift` / `HomeView.swift`, `berkeley-mobile/Safety/SafetyViewModel.swift` / `SafetyView.swift`, `berkeley-mobile/Events/EventDataSource/EventsViewModel.swift` / `berkeley-mobile/Events/EventsView.swift`.
- **SwiftUI views are suffixed `View`**, e.g. `HomeView`, `SafetyView`, `TodayView`, `GuidesView`, `FeedbackFormView`. **UIKit view controllers are suffixed `ViewController`**, e.g. `MapViewController`, `GymDetailViewController`, `LibraryDetailViewController`, `DrawerViewController`.
- **Firestore-backed data-access types are suffixed `DataSource`** and conform to the `DataSource` protocol (`berkeley-mobile/Data/DataSource.swift`), e.g. `LibraryDataSource`, `GymDataSource`, `GymClassDataSource`, `MapDataSource`. Each lives in its own sub-folder named after itself (e.g. `Home/Libraries/LibraryDataSource/`), alongside its model type(s).
- **Shared model-capability protocols are named descriptively as `Has*`/`Can*` predicates**, e.g. `HasLocation`, `HasImage`, `HasName`, `HasOpenTimes`, `HasOpenClosedStatus`, `HasPhoneNumber`, `HasWebsite`, `CanFavorite` (all in `berkeley-mobile/Data/ItemProtocols/`). Delegate protocols are named `<Feature>Delegate`, e.g. `DrawerViewDelegate`, `MainDrawerViewDelegate`, `SearchDrawerViewDelegate`, `FilterViewDelegate`, `FeedbackFormPresenterDelegate`.
- Firestore collection-name string constants use a `k`-prefixed camelCase convention scoped `fileprivate` to the data source that uses them, e.g. `fileprivate let kLibrariesEndpoint = "Libraries"` in `LibraryDataSource.swift`, `fileprivate let kGymsEndpoint = "Gyms"` in `GymDataSource.swift`. This differs from the `BMConstants`-centralized approach used by `BMNetworkingManager` (`BMConstants.safetyLogsCollectionName`) — two conventions coexist as observed in the sampled files.

## File Organization

- Each feature under `berkeley-mobile/` is organized as a folder containing its `View`/`ViewController` files directly, with data-access code (`*DataSource` + model) nested one level deeper in a sub-folder sharing the data source's name (e.g. `Home/Fitness/GymDataSource/`, `Home/Fitness/GymClassDataSource/`, `Home/Fitness/GymOccupancy/`).
- Shared, cross-feature code is centralized under `berkeley-mobile/Data/` (data layer: `DataManager`, `DataSource` protocol, `ItemProtocols/`, `PropertyWrappers/`) and `berkeley-mobile/Common/` (reusable SwiftUI view components, further split into `DetailView/`, `FilterView/`, `Images/` sub-folders by concern).
- Extensions on Foundation/UIKit types are collected under `berkeley-mobile/Utils/`, named `<Type>+Extension.swift` or `<Type>+Extensions.swift` (both plural forms are present, e.g. `CLLocation+Extension.swift` vs. `UIStackView+Extensions.swift`).
- Dependency-injection container extensions are centralized in a single file at the target root: `berkeley-mobile/BerkeleyMobile+Injection.swift`.

## Architectural Patterns

- **MVVM is the dominant pattern for SwiftUI-based features**: a `ViewModel` class conforms to `ObservableObject` and exposes `@Published` state; the paired `View` struct consumes it, generally injected via the `Factory` package's `@Injected`/`@InjectedObject` property wrappers rather than passed through initializers (e.g. `MainContainerViewController` uses `@Injected(\.homeViewModel) private var homeViewModel`; `TabBarController` uses `@Injected(\.feedbackFormPresenter) private var feedbackFormPresenter`).
- One observed exception uses the newer Observation-framework style instead of `ObservableObject`: `berkeley-mobile/Debug/DebugViewModel.swift` is declared `@Observable` (per repository survey; framework capability provided by Swift's `Observation` module, Level 2 — the repository's specific usage of `@Observable` on this one type is Level 1).
- **UIKit view controllers are used for a minority of features** (`MapViewController`, `GymDetailViewController`, `LibraryDetailViewController`, and the `Drawer/` module), generally the older parts of the codebase — file header comments in `berkeley-mobile/Drawer/DrawerViewController.swift` and `berkeley-mobile/AppDelegate.swift` reference the original project name `bm-persona` and author "RJ Pimentel," while newer files (2024–2026 copyright headers) are attributed to "ASUC OCTO" and follow the SwiftUI/MVVM pattern. UIKit view controllers are bridged into the SwiftUI hierarchy via `UIHostingController` (SwiftUI embedding UIKit is not observed; the reverse — UIKit screens embedding SwiftUI, and SwiftUI tabs wrapping UIKit-based detail screens via `UIViewControllerRepresentable`, e.g. `GymDetailView` wrapping `GymDetailViewController` per the feature survey — is the pattern used).
- **Singletons are used for shared app-wide services**: `DataManager.shared`, `BMNetworkingManager.shared`, `BMLocationManager.shared` (referenced in `AppDelegate.swift`). This is a repository-wide convention for cross-cutting services, distinct from the per-feature `Factory`-managed view models.
- **Protocol composition for models**: feature model structs conform to multiple small `ItemProtocols/` protocols rather than inheriting from a shared base class, e.g. `struct BMLibrary: HomeDrawerSectionRowItemType, CanFavorite, HasPhoneNumber, HasOpenTimes` (`berkeley-mobile/Home/Libraries/LibraryDataSource/BMLibrary.swift`), where `HomeDrawerSectionRowItemType` (defined in `HomeViewModel.swift`) is itself a protocol composing `HasLocation, SearchItem, HasImage, Identifiable, Equatable`.
- **Property wrappers for cross-cutting model concerns**: `@Display` (`berkeley-mobile/Data/PropertyWrappers/Display.swift`) is applied to model string fields intended for UI display, to normalize whitespace/invalid characters at the point of assignment (e.g. `@Display var name: String`, `@Display var description: String?` in `BMLibrary`).
- **`#if DEBUG` conditional compilation** gates developer-only code paths, e.g. the debug menu presentation in `berkeley-mobile/TabBarController.swift` and the `debugViewModel` `Factory` definition in `berkeley-mobile/BerkeleyMobile+Injection.swift`.

## Error Handling

- A single localized error enum, `BMError` (`berkeley-mobile/Data/BMError.swift`), is used for calendar-related failures, conforming to `LocalizedError` and providing `NSLocalizedString`-wrapped messages.
- Firestore errors in the callback-based `DataSource` implementations are logged via `print(...)` and otherwise dropped (no completion call, no user-facing surfacing) — see `docs/api-standards.md` for the specific call sites.
- Firestore errors in the `async`/`await` `BMNetworkingManager` path are propagated with `throws`/`try await` and caught by view models, which set a `@Published var alert: BMAlert?` to drive a SwiftUI alert (e.g. `berkeley-mobile/Safety/SafetyViewModel.swift`).

## Dependency Management

- Two dependency-management systems coexist in the repository: CocoaPods (`Podfile`, `Podfile.lock`, checked-in `Pods/` — used for Firebase and GoogleSignIn) and Swift Package Manager (`XCRemoteSwiftPackageReference` entries in `project.pbxproj` — used for `Factory`/`FactoryKit` and `Glur`).
