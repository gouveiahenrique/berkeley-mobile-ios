# Code Conventions

## Naming Conventions

- LEVEL 1 — Many model, manager, and view types use a `BM` prefix (Berkeley Mobile), e.g. `BMDiningHall`, `BMGym`, `BMLocationManager`, `BMNetworkingManager`, `BMConstants`, `BMError`, `BMAlert`, `BMColor`, `BMDrawerView`, `BMSafetyLog`. Confirmed via repository-wide search of `class BM*` / `struct BM*` / `enum BM*` declarations (28+ distinct types). Not all types follow this prefix — e.g. `DataManager`, `HomeViewModel`, `MapDataSource` do not use it — so `BM` appears to mark reusable/shared or model types rather than being a universal rule.
- LEVEL 1 — View model classes are named with a `ViewModel` suffix (e.g. `HomeViewModel`, `SafetyViewModel`, `GuidesViewModel`, `WeatherDataViewModel`, `GymOccupancyViewModel`, `FeedbackFormViewModel`, `DebugViewModel`) — 13 files match `*ViewModel.swift`.
- LEVEL 1 — SwiftUI view structs conform to `View` directly (47 files with `: View {`), typically named with a `View` suffix (e.g. `HomeView`, `SafetyView`, `DetailView`, `FilterView`).
- LEVEL 1 — Per-feature Firestore data source types are named `<Feature>DataSource` (`MapDataSource`, `LibraryDataSource`, `GymDataSource`, `GymClassDataSource`), each conforming to the `DataSource` protocol and located in a `<Feature>DataSource/` subfolder.
- LEVEL 1 — File-local/module-private constants (Firestore collection names, UI sizing values) are declared as `fileprivate let k<Name>` (occasionally `private let k<Name>`) at file scope, e.g. `fileprivate let kMapEndpoint = "Map Marker"`, `fileprivate let kGymsEndpoint = "Gyms"`, `fileprivate let kViewMargin`, `fileprivate let kButtonPadding`. This `k`-prefix convention is used consistently across at least 18 distinct constants found via search, across both data-source files and SwiftUI layout files.
- LEVEL 1 — Swift extension files follow the `<Type>+Extension.swift` or `<Type>+Extensions.swift` naming pattern under `berkeley-mobile/Utils/` (e.g. `Date+Extension.swift`, `CLLocation+Extension.swift`, `UIView+Extensions.swift`, `UserDefaults+Extension.swift`); two files use a shortened `+Ext.swift` suffix instead (`TimeInterval+Ext.swift`, `Logger+Ext.swift`).
- LEVEL 1 — `UserDefaults` keys are centralized in a `UserDefaultsKeys: String` enum (`berkeley-mobile/Utils/UserDefaults+Extension.swift`) rather than raw string literals at call sites, accessed through generic `UserDefaults` extension methods (`set<T>(_:forKey: UserDefaultsKeys)`, `integer(forKey:)`, `data(forKey:)`, `increment(forKey:)`).

## File Organization

- LEVEL 1 — The files inspected in this session begin with a standard header comment block: filename, project name, author ("Created by ..."), and copyright line (e.g. `// AppDelegate.swift`, `// berkeley-mobile`, `// Created by RJ Pimentel on 10/23/19.`, `// Copyright © 2019 RJ Pimentel. All rights reserved.` or `© <year> ASUC OCTO.` in newer files). This pattern was observed in every file read during this analysis; exhaustive verification across all files was not performed.
- LEVEL 1 — Code within files is segmented using `// MARK:` comments (124 occurrences repository-wide via `grep`), e.g. `// MARK: - Safety`, `// MARK: Migration Actions`, `// MARK: UISceneSession Lifecycle`.
- LEVEL 1 — Indentation uses 4 spaces, not tabs (confirmed on `HomeViewModel.swift`: 65 lines beginning with 4 spaces, 0 lines beginning with a tab character).
- LEVEL 1 — Feature folders group a screen's `View`, `ViewModel`, and any feature-specific `DataSource`/model files together (e.g. `Safety/` holds `SafetyView.swift`, `SafetyViewModel.swift`, `SafetyMapView.swift`, `SafetyMapMarker.swift`; `Home/Fitness/` holds `FitnessView.swift`, `GymDetailViewController.swift`, `GymDataSource/`, `GymClassDataSource/`, `GymOccupancy/`).

## Architectural Patterns

- LEVEL 1 — The SwiftUI portions of the app follow an MVVM pattern: `ObservableObject`/`@Observable` view-model classes expose `@Published`/observed state consumed by `View` structs (e.g. `HomeViewModel` + `HomeView`, `SafetyViewModel` + `SafetyView`). 6 files use `ObservableObject`; 10 files use the newer `@Observable` macro — both patterns coexist in the repository (e.g. `HomeViewModel: ObservableObject` vs. `WeatherDataViewModel`/`GymOccupancyViewModel` using `@Observable`).
- LEVEL 1 — A `Presenter` naming/pattern appears once, in `FeedbackForm/FeedbackFormPresenter.swift`, which is constructed from and wraps a `FeedbackFormViewModel` (see `BerkeleyMobile+Injection.swift`: `feedbackFormPresenter` factory depends on `feedbackFormViewModel`). Not found in codebase: this presenter pattern reused elsewhere in the app.
- LEVEL 1 — Legacy UIKit screens (`MapViewController`, `GymDetailViewController`, `LibraryDetailViewController`, `SearchDrawerViewController`, `DrawerViewController`) are bridged into the SwiftUI hierarchy via `UIViewControllerRepresentable` conformances rather than being rewritten, indicating an incremental UIKit-to-SwiftUI migration in progress.
- LEVEL 1 — Dependency injection is handled through `FactoryKit`: the cross-feature view-model instances inspected in this session are declared in `berkeley-mobile/BerkeleyMobile+Injection.swift` as `Factory<T>` properties on `Container`, with explicit lifetime annotations (`.shared`, `.singleton`, or default/unscoped).
- LEVEL 1 — Reusable value-formatting behavior is implemented via Swift property wrappers, e.g. `@Display` (`berkeley-mobile/Data/PropertyWrappers/Display.swift`) trims whitespace and strips a specific invalid character (`�`) from `String`/`String?` fields on model types (used on `BMEventCalendarEntry.name`, `.descriptionText`, `.location`).
- LEVEL 1 — Concurrency is expressed with a mix of `DispatchGroup`-based completion-handler chaining (`DataManager.fetch`, `HomeViewModel.fetchHomeSectionsData`) and Swift structured concurrency (`async`/`await`, `Task`, `Task.detached`, `withTaskGroup`) in newer files (`BMNetworkingManager`, `GymOccupancyViewModel`, `WeatherDataViewModel`). Not found in codebase: a stated policy on which concurrency style to use for new code — both are present depending on file age/author.

## Error Handling

- LEVEL 1 — Firestore call sites in the older `DataSource` conformers (`MapDataSource`, `LibraryDataSource`, `GymDataSource`, `GymClassDataSource`) handle errors by `print`-ing a formatted message (e.g. `print("[Error @ MapDataSource.fetchItems()]: \(err)")`) and returning early, without surfacing the error to the UI layer.
- LEVEL 1 — Newer `async`/`await` code paths (`BMNetworkingManager`, `SafetyViewModel.listenForSafetyLogs`, `WeatherDataViewModel`) use Swift's `throws`/`try`/`catch` and surface failures to observable state consumed by the UI (`self.alert = BMAlert(...)`, `self.showNotAvailable = true`) or a `Logger` call (`Logger.weatherDataViewModel.error(...)`, `berkeley-mobile/Utils/Logger+Ext.swift`).
- LEVEL 1 — App-specific domain errors are modeled as a `BMError: Error` enum conforming to `LocalizedError` with human-readable `errorDescription` strings (`berkeley-mobile/Data/BMError.swift`), covering calendar-integration failure cases (`insufficientAccessToCalendar`, `eventAlreadyAddedInCalendar`, etc.).
