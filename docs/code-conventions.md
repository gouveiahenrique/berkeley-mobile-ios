# Code Conventions

## Naming Conventions

- The repository prefixes most app-specific types with `BM` (Berkeley Mobile), e.g. `BMColor` (`berkeley-mobile/Assets/Colors/Colors.swift:13`), `BMAlert`, `BMError`, `BMConstants`, `BMLocationManager`, `BMNetworkingManager`, `BMEventCalendarEntry`, `BMEventManager`, `BMSafetyLog`, `BMDiningHall`, `BMGym`, `BMLibrary`, `BMMPDRoomInfo`. Not every type uses this prefix — e.g. `DataManager`, `DataSource`, `TabBarController`, `MapViewController`, `HomeViewModel`, `EventsViewModel`, `SafetyViewModel`, `DiningHallsViewModel` do not — so the prefix is observed as common but not universal.
- View-model classes are named `<Feature>ViewModel` (e.g. `HomeViewModel`, `SafetyViewModel`, `EventsViewModel`, `DiningHallsViewModel`, `GuidesViewModel`, `FeedbackFormViewModel`, `DebugViewModel`, `SearchViewModel`), each registered as a `Factory<...>` in `berkeley-mobile/BerkeleyMobile+Injection.swift:12-96`.
- SwiftUI view types are named `<Feature>View` (e.g. `TodayView`, `SafetyView`, `ResourcesView`, `HomeView`, `FeedbackFormView`, `DebugView`), referenced in `berkeley-mobile/TabBarController.swift:17-20` and `BerkeleyMobile+Injection.swift`.
- UIKit view-controller types are named `<Feature>ViewController` (e.g. `MapViewController`, `MainContainerViewController`, `TabBarController`, `DrawerViewController`, `SearchDrawerViewController`).
- Data-source types conforming to the `DataSource` protocol are named `<Feature>DataSource` and grouped in a `<Feature>DataSource/` subfolder (e.g. `MapDataSource/MapDataSource.swift`, `LibraryDataSource/LibraryDataSource.swift`, `GymDataSource/GymDataSource.swift`, `GymClassDataSource/GymClassDataSource.swift`).
- Firestore collection-name constants are declared `fileprivate` at file scope with a `k`-prefix, e.g. `kMapEndpoint`, `kLibrariesEndpoint`, `kGymsEndpoint`, `kGymClassesEndpoint`, `kEventsDataServiceEndpoint`, `kDiningHallEndpoint`, `kDiningHallAdditionalDataEndpoint` (see individual data-source/view-model files).
- Extensions on Foundation/UIKit types follow a `Type+Extension.swift` or `Type+Ext.swift` file-naming pattern in `berkeley-mobile/Utils/` (e.g. `Date+Extension.swift`, `String+Extension.swift`, `UIView+Extensions.swift`, `UserDefaults+Extension.swift`, `Logger+Ext.swift`, `CLLocation+Extension.swift`, `NSCoding+Extension.swift`, `TimeInterval+Ext.swift`, `Collection+Extension.swift`, `View+Extension.swift`, `UIImage+Extensions.swift`, `UIDevice+Extensions.swift`, `UIScrollView+GestureRecognizer.swift`).
- Protocols describing item capabilities are named `Has<Capability>` or `Can<Capability>`, grouped in `berkeley-mobile/Data/ItemProtocols/` (e.g. `HasImage`, `HasLocation`, `HasName`, `HasOpenClosedStatus`, `HasOpenTimes`, `HasPhoneNumber`, `HasWebsite`, `CanFavorite`, plus `SearchItem` and `BMCalendarEvent`).

## File Organization

- The repository organizes source files by feature/domain folder under `berkeley-mobile/` (see `docs/structure.md`), with each feature folder colocating its view, view model, and (where present) data source.
- Singletons expose a static `shared` instance property, e.g. `DataManager.shared` (`berkeley-mobile/Data/DataManager.swift:21`), `BMNetworkingManager.shared` (`berkeley-mobile/Data/BMNetworkingManager.swift:13`), `BMLocationManager.shared` (`berkeley-mobile/Data/BMLocationManager.swift:28`), `EventsDataService.shared` (`berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:36`).
- `// MARK: -` comments are used throughout to delimit logical sections within a file (e.g. `berkeley-mobile/AppDelegate.swift:54,74`, `berkeley-mobile/Data/BMNetworkingManager.swift:18,29`, `berkeley-mobile/Home/Map/MapViewController.swift:34,309,338`).

## Architectural Patterns

- The repository implements an MVVM-influenced structure for SwiftUI-backed features: a `ViewModel` class conforming to `ObservableObject` (with `@Published` properties, e.g. `HomeViewModel`, `berkeley-mobile/Home/HomeViewModel.swift:34-42`; `SafetyViewModel`, `berkeley-mobile/Safety/SafetyViewModel.swift:57-73`) or, in newer code, Swift's `@Observable` macro (e.g. `DiningHallsViewModel`, `berkeley-mobile/Home/Dining/DiningDataSource/DiningHallsViewModel.swift:17-18`; `EventsViewModel`, `berkeley-mobile/Events/EventDataSource/EventsViewModel.swift:76-78`).
- The repository implements dependency injection via the `FactoryKit` package rather than initializer injection at call sites in most feature areas: dependencies are declared as `Factory<T>` properties on `Container` (`berkeley-mobile/BerkeleyMobile+Injection.swift`) and resolved with `.resolve()` or the `@Injected(\.propertyName)` property wrapper (e.g. `berkeley-mobile/TabBarController.swift:15`).
- The repository implements a shared `DataSource` protocol (`berkeley-mobile/Data/DataSource.swift:11-16`) with a completion-handler-based async contract for three data sources (`Map`, `Library`, `Gym`), coordinated by the singleton `DataManager`. Newer data-fetching code (Events, Dining, Safety/Resources) instead implements `async`/`await` Firestore calls directly within a dedicated service or view-model class, without conforming to `DataSource`.
- The repository implements custom property wrappers for domain rules, e.g. `@Display` (`berkeley-mobile/Data/PropertyWrappers/Display.swift:12`), which trims whitespace and strips invalid characters from string values on write.
- The repository implements a custom drawer/bottom-sheet UI abstraction (`berkeley-mobile/Drawer/`) using protocol-oriented design: `DrawerViewDelegate` and `MainDrawerViewDelegate` protocols provide default implementations via protocol extensions (e.g. `berkeley-mobile/Drawer/DrawerViewDelegate.swift:36-129`, `berkeley-mobile/Drawer/MainDrawerViewDelegate.swift:22-106`) rather than base-class inheritance.
- The repository embeds UIKit view controllers inside SwiftUI via `UIViewControllerRepresentable` (e.g. `HomeMapView` wrapping `MapViewController`, `berkeley-mobile/Home/Map/MapViewController.swift:17-31`) and embeds SwiftUI views inside UIKit via `UIHostingController` (e.g. `berkeley-mobile/TabBarController.swift:17-20`), indicating an incremental UIKit-to-SwiftUI migration rather than a single consistent UI framework.

## Error Handling

- The repository defines an app-specific `Error` enum, `BMError` (`berkeley-mobile/Data/BMError.swift:11-16`), conforming to `LocalizedError` to provide user-facing messages (lines 18-31), used specifically for calendar-integration failures.
- Completion-handler-based Firestore calls in `DataSource` conformers log errors to the console via `print(...)` and otherwise silently return without invoking the completion handler (e.g. `berkeley-mobile/Home/Map/MapDataSource/MapDataSource.swift:24-26`, `berkeley-mobile/Home/Libraries/LibraryDataSource/LibraryDataSource.swift:25-27`).
- `async`/`await`-based services log errors using the unified logging system (`os.Logger`, declared per-view-model in `berkeley-mobile/Utils/Logger+Ext.swift:12-51`) and/or surface them to the UI via a `BMAlert` published property (e.g. `berkeley-mobile/Safety/SafetyViewModel.swift:95-98`, `berkeley-mobile/Home/Dining/DiningDataSource/DiningHallsViewModel.swift:48,87`).

## Configuration Management

- Firestore collection names are hardcoded as Swift string constants local to each fetching file/class rather than centralized in one configuration file, e.g. `kGymsEndpoint = "Gyms"` (`berkeley-mobile/Home/Fitness/GymDataSource/GymDataSource.swift:12`). Some collection names are instead centralized in `BMConstants` (referenced as `BMConstants.safetyLogsCollectionName` and `BMConstants.resourceCategoriesCollectionName` in `berkeley-mobile/Data/BMNetworkingManager.swift:21,32`), so both patterns are present in the repository.
- App-level constants (e.g. map bounds, section titles) are centralized in `berkeley-mobile/Data/BMConstants.swift`, referenced as `BMConstants.mapBoundsRegion`, `BMConstants.diningSectionTitle`, etc. (e.g. `berkeley-mobile/Home/Map/MapViewController.swift:126`, `berkeley-mobile/Home/HomeViewModel.swift:21`).
- Secrets/credentials (`GoogleService-Info.plist`, production Firebase API key) are excluded from the repository per `README.md:28`.
