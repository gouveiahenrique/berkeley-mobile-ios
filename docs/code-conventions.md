# Code Conventions

Evidence for this document comes from direct inspection of source files across the repository (via CodeGraph symbol exploration and targeted reads). No linter or formatter configuration (e.g. `.swiftlint.yml`, `.swiftformat`) was found in the repository, so the conventions below are observed patterns, not tool-enforced rules.

## Naming Conventions

- **`BM` prefix for domain model / manager types**: 20 files match `BM*.swift` (e.g. `BMConstants.swift`, `BMError.swift`, `BMEventManager.swift`, `BMLocationManager.swift`, `BMNetworkingManager.swift`, `BMColor` in `Colors.swift`, `BMEventCalendarEntry.swift`, `BMSafetyLog` in `SafetyViewModel.swift`, `BMAlert.swift`, `BMFont` referenced in `GymOccupancyWidget.swift`). This prefix is applied to app-specific domain types (managers, constants, errors, models, design tokens), distinguishing them from framework types (`UIColor`, `UIView`) and from feature-specific view/view-model types which do not use the prefix (e.g. `HomeViewModel`, `SafetyView`).
- **`*ViewModel` suffix for `ObservableObject` view models**: 13 files match `*ViewModel.swift` (e.g. `HomeViewModel.swift`, `SafetyViewModel.swift`, `EventsViewModel.swift`, `GuidesViewModel.swift`, `WeatherDataViewModel.swift`, `DiningHallsViewModel.swift`). Observed view models (`HomeViewModel`, `SafetyViewModel`) declare `class ... : ObservableObject` (or `NSObject, ObservableObject`) with `@Published` properties for SwiftUI state.
- **`*DataSource` suffix for Firestore-backed fetch types**: e.g. `MapDataSource`, `GymDataSource`, `GymClassDataSource`, `LibraryDataSource`, each conforming to the `DataSource` protocol (`berkeley-mobile/Data/DataSource.swift`) and located in a subfolder named after the type (e.g. `Home/Map/MapDataSource/MapDataSource.swift`).
- **`fileprivate let k<Name>` for endpoint/collection-name constants**: each `*DataSource.swift` file declares a `fileprivate let k<Feature>Endpoint = "<Collection Name>"` constant at file scope (e.g. `kMapEndpoint = "Map Marker"` in `MapDataSource.swift:13`, `kGymsEndpoint = "Gyms"` in `GymDataSource.swift:12`, `kLibrariesEndpoint = "Libraries"` in `LibraryDataSource.swift:12`, `kGymClassesEndpoint = "Gym Classes"` in `GymClassDataSource.swift:12`).
- **Nested `private struct Constants` / `ArgumentNames`** for grouping type-local constants: e.g. `MapViewController.Constants` (`berkeley-mobile/Home/Map/MapViewController.swift:38`), `BMEventCalendarEntry.ArgumentNames` (`berkeley-mobile/Events/EventDataSource/BMEventCalendarEntry.swift:12-22`).
- **`// MARK: -` section comments** are used consistently across files to delineate logical sections (e.g. protocol conformance extensions, constant groups, sample-data extensions). Observed in `AppDelegate.swift`, `Colors.swift`, `BMNetworkingManager.swift`, `SafetyViewModel.swift`, `GymOccupancyWidget.swift`, `TabBarController.swift`.

## File Organization

- **One primary type per file**, file name matching the type name (e.g. `MapDataSource.swift` defines `class MapDataSource`, `HomeViewModel.swift` defines `class HomeViewModel`).
- **Feature-scoped subfolders that mirror type names** for data-source types: `Home/Map/MapDataSource/MapDataSource.swift`, `Home/Fitness/GymDataSource/GymDataSource.swift`, `Home/Fitness/GymClassDataSource/GymClassDataSource.swift`, `Home/Libraries/LibraryDataSource/LibraryDataSource.swift`, `Events/EventDataSource/` (containing both `BMEventCalendarEntry.swift` and `EventsViewModel.swift`).
- **`Data/ItemProtocols/`** groups small, single-responsibility protocols shared across domain models (`HasImage.swift`, `HasLocation.swift`, `HasName.swift`, `HasOpenClosedStatus.swift`, `HasOpenTimes.swift`, `HasPhoneNumber.swift`, `HasWebsite.swift`, `CanFavorite.swift`, `SearchItem.swift`, `BMCalendarEvent.swift`) — domain models compose several of these via protocol conformance (e.g. `BMEventCalendarEntry: NSObject, NSCoding, Identifiable, BMCalendarEvent, HasImage, CanFavorite`, `BMEventCalendarEntry.swift:11`).
- **`Data/PropertyWrappers/`** holds custom property wrappers (`Display.swift`), used as `@Display var name: String` on domain model properties (`BMEventCalendarEntry.swift:25,28,29`).
- **Per-feature `Colors+<Feature>.swift` extension files** extend a common `BMColor` struct/namespace (base declared in `Assets/Colors/Colors.swift`) rather than declaring feature colors inline in each feature file: `Colors+ActionButton.swift`, `Colors+AlertView.swift`, `Colors+Calendar.swift`, `Colors+Event.swift`, `Colors+GymClass.swift`, `Colors+MapMarker.swift`, `Colors+Resource.swift`, `Colors+StudyPact.swift`, `Colors+TagView.swift`, `Colors+Text.swift`.

## Architectural Patterns

- **Singleton managers** for cross-cutting services: `DataManager.shared` (`Data/DataManager.swift:21`), `BMNetworkingManager.shared` (`Data/BMNetworkingManager.swift:13`), `BMLocationManager.shared` (referenced in `AppDelegate.swift:25`).
- **Protocol-oriented data fetching**: the `DataSource` protocol (`Data/DataSource.swift`) is the shared contract for type-level `fetchItems`/`fetchDispatch`, implemented independently per feature rather than through a shared base class.
- **Dependency injection via `FactoryKit`**: view models/services are registered once in `berkeley-mobile/BerkeleyMobile+Injection.swift` as `Container` extension properties returning `Factory<T>` with an explicit lifetime (`.shared`, `.singleton`, or default/unscoped), and obtained at call sites via `@Injected(\.propertyName)`.
- **UIKit-hosts-SwiftUI composition**: root navigation and container view controllers are UIKit (`UITabBarController`, `UIViewController` subclasses), which embed SwiftUI feature screens via `UIHostingController(rootView:)` (`TabBarController.swift:17-20`, `MainContainerViewController.swift:34-35`).
- **`DrawerViewDelegate` / `MainDrawerViewDelegate` protocol with default implementations via `extension ... where Self: UIViewController`**: `berkeley-mobile/Drawer/MainDrawerViewDelegate.swift` implements drawer-stack management (`dismissTop`, `coverTop`, `hideTop`, `showTop`, `moveCurrentDrawer`, `showMainDrawer`) as protocol extension methods rather than a base class, allowing multiple view controllers to opt into drawer behavior.
- **`async`/`await` combined with completion-handler style**: newer code (`BMNetworkingManager`, added per file header "Created by Justin Wong on 5/15/25") uses Swift concurrency (`async throws`), while older `DataSource` implementations (headers dated 2019–2020) use completion-handler closures. Both patterns coexist in the current codebase; `DataManager.fetch(source:_:)` bridges the completion-handler style with `DispatchGroup`-based deduplication.
- **Copyright header convention**: nearly every Swift file opens with a standard header comment block (file name, target name/`bm-persona` or `berkeley-mobile`, creation attribution "Created by <name> on <date>", and a copyright line — early files say "Copyright © <year> RJ Pimentel", files from 2024 onward say "Copyright © <year> ASUC OCTO"). This is a repository-wide file-header convention, observed consistently across sampled files (`AppDelegate.swift`, `DataManager.swift`, `BMNetworkingManager.swift`, `MapDataSource.swift`, `HomeViewModel.swift`, `GymOccupancyWidget.swift`).
